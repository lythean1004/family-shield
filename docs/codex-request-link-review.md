## 1. 확인된 문제 (먼저 고칠 것)

> **2026-11-26 Claude Code가 고침(운영자 요청).** `links.js`에서 `도메인@도메인` 모양(앞이 알려진 끝부분의 도메인)을 링크 하나로 잡아 `SIG_DECEPTIVE_URL` → 위험. 이메일(`help@example.com`, `john.doe@gmail.com`)은 그대로. Codex는 이 수정의 경계(아래 2-1)를 다시 확인해 주세요.

**스킴 없는 ‘공식@가짜’가 공식 링크로 통과한다.**

| 입력 | 지금 결과 | 기대 |
|---|---|---|
| `결제 확인 naver.com@pay-check.xyz/login` | `SIG_LINK, SIG_OFFICIAL_LINK` → 확인 필요 + “공식 주소로 보이는 링크” | 공식 링크 아님. `SIG_DECEPTIVE_URL` → 위험(R11) |
| `결제 확인 https://naver.com@pay-check.invalid/login` | 위험(R11) | 그대로 |

- 원인으로 보이는 것: `links.js`의 `BARE_DOMAIN_RE`는 `@` 뒤 도메인을 잡지 않아(이메일 보호) `naver.com`만 링크로 잡는다. 그래서 `@` 뒤의 진짜 목적지가 사라진다.
- 확인할 것: 휴대폰 문자 앱이 이 모양을 웹 링크로 여는지, 이메일로 여는지는 기기마다 다를 수 있다. 어느 쪽이든 **“공식 주소로 보이는 링크”라고 표시하면 안 된다.**
- 제안:
  - `호스트@호스트/경로` 모양(앞뒤가 모두 도메인이고 뒤에 경로가 있음)을 속임수로 잡는다.
  - 평범한 이메일(`help@example.com`)은 링크·속임수로 보지 않는다.
  - 경계를 시험으로 고정한다.

## 2. 교차 검토 (가짜를 공식으로 보는 경우 찾기)

아래 모양마다 `extractCodeSignals` → `decide` 결과를 표로 남긴다. 기대와 다르면 시험부터 쓰고 고친다.

1. **주소 앞부분 속임수:**
   - 퍼센트 인코딩 `%40`
   - 역슬래시 `naver.com\@가짜`
   - 사용자명·비밀번호 `naver.com:pw@가짜`
   - 대문자 `HTTPS://`
   - 앞뒤 공백·괄호, 마크다운 링크 `[www.hometax.go.kr](https://가짜)`(보이는 글과 실제 주소가 다름)
2. **호스트 흉내:**
   - `hometax.go.kr.가짜.xyz`, `hometax-go-kr.xyz`
   - 끝에 점 `hometax.go.kr.`, 포트 `:8080`
   - 전각 점·전각 슬래시(`．` `／`)
   - 퓨니코드·한글 도메인(`xn--`)
   - IP 주소
3. **공식 도메인 안의 위험:**
   - 넘겨주기(`?url=`, `?redirect=`, `/r/https://…`)
   - 공식 포털 하위의 누구나 만드는 주소(블로그·카페·폼·오픈채팅)
   - `go.kr` 하위라도 사칭이 가능한 모양이 있는지
4. **여러 링크:** 공식 + 가짜가 섞이면 공식 예외가 꺼지는지, 같은 공식 주소가 두 번이면 어떤지.
5. **단축 주소 대조(D48 ①):**
   - 정규화 일치 확인: 대소문자, 끝의 `/`·문장부호, `?`·`#` 뒤, `www.`
   - 코드 1~2글자 제외가 잘 되는지
   - `data/kisa/`로 로컬 확인:
     - 목록 키 수(20,425)를 다시 만들어 같은지
     - 서비스로 본 42곳(`data/kisa/services.json`) 중 단축 서비스가 아니라 일반 사이트로 보이는 호스트가 있는지
     - 그런 곳의 흔한 경로(`/login`, `/index` 등)가 키에 들어가 정상 주소를 잡을 위험이 있는지
   - 표본 20개를 **링크를 열지 않고** 글자 모양만 사람이 판단할 수 있게 요약한다. 문서에는 원문 대신 호스트·경로 길이·패턴만 쓴다.
6. **D49 경계:** 공식 주소만 있는 문자에서 AI 재촉·돈·비밀을 무시해도 위험을 놓치지 않는지 확인한다. 개인정보·선입금·개인 계좌·전화 유도·앱 설치는 위험으로 남아야 한다. 코드가 찾는 재촉·돈 표현으로 충분한지, 놓칠 만한 흔한 표현을 3~5개 제안한다(구현은 운영자 승인 후).

## 3. 공식 주소 카드 확대 (출처가 확인되는 것만)

운영자 바람: 정부, 공식 은행, 상장기업 등 공적으로 확인된 주소에 “공식 주소로 보이는 링크”가 표시되면 좋겠다.

- **지금 들어 있는 것:**
  - `official-domains.json` 40장: 정부 `go.kr` 전체·`gov.kr`, 주요 은행 8, 카드 8, 택배, 통신 3사, 건강보험·국민연금·금감원 등
  - `official-link-hosts.json`: 포털 첫 화면 4곳
- **우선순위 1, 금융회사:**
  - 대상: 케이뱅크, SC제일, 한국씨티, 지방은행(부산·경남·iM뱅크·광주·전북·제주), 수협, 신협, 새마을금고, 산업·수출입은행, 주요 증권사·보험사
  - 출처: 금융감독원 ‘금융회사 정보’ 같은 공공 목록, 또는 회사 공식 누리집 안의 자기 주소 안내
  - 카드마다 기록: 출처 URL, 게시일, 확인일, 이용조건 확인 여부
- **우선순위 2, 부모님이 자주 받는 생활 서비스·상장기업:**
  - 예시: 대형 유통·항공·전력·가스·수도
  - 회사마다 출처 확인이 필요하니 10곳 안팎으로 시작한다. 목록을 먼저 제안하고, 운영자가 고른 곳만 넣는다.
- **넣지 말 것:**
  - 누구나 하위 주소·글을 만들 수 있는 도메인(포털 하위, 클라우드 호스팅, 쇼핑몰 입점 페이지)
  - 출처 없이 “유명하니까” 넣는 것
- 확인할 것:
  - 새 카드마다 KISA 목록·Tranco 대조 결과를 남긴다(요청서 3과 같은 방식).
  - 새 카드가 KISA 호스트 키를 지우게 되면 그 수를 보고한다.
