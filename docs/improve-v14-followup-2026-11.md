독립 v14 최초 성적은 위험 놓침 29/41(70.7%), 위험 오경보 0/79였다. 이 기록의 검증은 이미 개발에 사용한 이전 판본에서 진행했다. v14 사례와 정답은 추가로 열지 않았다. [v14 최초 채점 기록](improve-v13-to-v14-2026-11.md)

## 현재 신호로 두 목표를 달성할 수 있는지

제품 `5285bca`에서 외부 AI·주소 평판·도메인 생성일 조회를 끄고 각 문장을 다시 판정했다. 규칙 엔진이 받는 신호 집합, 발신 기관과 연결할 수 없는 행동 집합, 부모의 세 응답(현재 통화·이전 통화·가족의 발신 부인)이 같은 입력을 한 묶음으로 만들었다. 기본 계산에서는 응답하지 않은 경우와 명시적으로 ‘아니요’를 선택한 경우도 구분했다. 등록된 번호 끝자리와 수신 번호 끝자리는 원래 입력대로 추출기에 전달했다.

한 묶음에는 규칙이 같은 등급을 줄 수밖에 없다. 그 묶음을 위험으로 정하면 안에 있는 위험 사례를 모두 잡는 동시에 비위험 사례에도 모두 경보를 낸다. 시험 정답을 전부 알고 있다는 가정 아래, 위험 오경보가 10% 미만인 모든 묶음 선택 중 잡을 수 있는 위험 건수의 최댓값을 계산했다. 운영에 적용할 판정표를 만들지는 않았다.

## 이전 작성자 6명의 놓침을 문장 근거로 재검토

v7~v9 개발 자료 360건에서 규칙 기준으로 놓친 23건을 모두 골랐다. 작성자마다 이미 잡은 위험 3건과 비위험 대조 5건을 더해 총 71건을 구성했다. 기존 오경보도 대조에 포함했다. 두 AI 검수자는 사례의 선택 이유·기존 등급·코드를 보지 않고 문장과 실제 부모 응답만 읽었다. 표시된 짧은 근거 298개가 본문 또는 입력값과 일치했다. AI 검수자 의견은 사용자 판정이나 정답 변경으로 사용하지 않았다.

놓친 23건 중 두 검수자가 같은 위험 규칙을 지지한 것은 11건, 한 명만 지지한 것은 2건, 두 명 모두 충분하다고 보지 않은 것은 10건이었다. 비위험 대조 30건에서 위험 근거가 충분하다고 본 검수자는 없었다. 같은 규칙을 지지한 사례도 제품에서 그 규칙을 발동할 근거가 실제로 남아 있는지 다시 확인했다.

- 세 작성자의 해외 결제·취소 연락 사례 3건은 실제 번호를 생략해 근거 카드의 공식 번호와 대조할 수 없었다. 관련 회귀 88개가 통과했다.
- 기관 사칭 의심 3건은 실제 목적지를 기록용 주소로 치환했거나 원번호를 생략했다. R147에서 허용한 별도 회신 경로라는 근거도 확인되지 않았다. 복구 비밀값 요구 1건과 부업 서류 묶음 1건도 원래 접수 주소가 남아 있지 않았다.
- 가족 관련 2건은 구매를 부탁한 사람과 구매해야 하는 사람, 또는 ‘막내’가 가족을 지칭하는지에 관해 해석이 갈렸다. 가족·통화·구매 관련 기존 회귀 191개가 통과했다. 물리적 분리 요구 1건도 타인의 도움을 차단하려는 요구인지 일시적인 거리두기인지 구분되지 않았다.
- 비위험 대조의 기존 위험 오경보 1건에는 부모의 ‘이전 통화 있음’ 선택과 링크가 있었지만, 서술에서는 다른 곳에 먼저 걸었던 통화였다. 최초 정답과 R2의 명시적 응답 처리는 그대로 기록했다.

## R152 · 통화 뒤 받은 설치 요구와 앞서 전화한 사람을 구분

R151에서 v2와 개발용 v7~v13의 합성 960건을 두 번 대조했다. 한번은 원래의 세 통화·가족 응답을 전달했고, 한번은 그 세 값만 빼고 분석했다. 원래 자료에는 명시적 답이 239건 있었고 적어도 하나가 긍정인 경우는 68건이었다. 규칙 기대 기준으로 원래 답을 전달하면 놓침이 107/329에서 60/329로 줄었고 위험 오경보는 0/631에서 1/631로 늘었다. 위험으로 바로잡힌 47건은 현재 통화 20건, 가족이 발신을 부인한 14건, 이전 통화와 실제 링크·설치 요구가 함께 있었던 13건이었다. 작성자 기대 기준은 놓침 94/316 → 63/316, 위험 오경보 0/644 → 17/644였다. 이 비교에는 합성 작성자가 원래 넣은 응답만 사용했다. 실제 이용자가 앞으로 어떻게 답할지는 측정하지 않았다.

남은 60건 중 긍정 응답이 있었던 4건은 전부 ‘앞서 전화를 받음’이었다. 이 4건과 이미 잡은 위험 4건, 비위험 6건의 문장과 원래 답만 검수자 두 명에게 보였다. 첫 작업표의 키 4쌍이 겹쳐 같은 문장과 순서로 14개 고유 키를 새로 부여했고 두 검수자 모두 각 행을 다시 대조했다. 판독 의견 변경은 없었다. 놓친 4건 중 둘 다 실제 설치 요구를 확인한 것은 1건이었다. 나머지는 앱을 찾는 방법, 기록에서 생략된 주소, 설치 대상이 생략된 설명이었다.

세 주제 단어군과 조정 모델의 0.50 제안을 코드의 R18에 더하는 방법도 로컬에서만 비교했다. 다른 작성자의 자유 형식 24건에서는 감지 1/8 → 7/8건, 오인 1/16 → 7/16건이었다. 같은 작성자의 현재형 18건에서는 감지 1/6 → 6/6건, 오인 0/12 → 1/12건이었다. 자유 형식에서 늘어난 오경보까지 고려해 이 조합으로 자동 위험 경보를 내리지 않았다.

## R174 · 앞서 소개한 발신자의 직원이 방문한 뒤 상환금을 받는 기록

앞 문장에서 금융회사 대출 담당자를 자처한 사람이 실제 발송자였음이 드러나고, 바로 다음 문장에서 그 직원의 방문과 수거가 같은 사건으로 확인되는 경우를 보완했다. 방문하는 직원은 상환금보다 먼저 등장해도 된다. 직원과 연결한 바로 그 방문 뒤에 수신자의 상환금·현금·수거 동사가 이어져야 한다. 서로 다른 방문을 한 사건으로 합치던 초안의 오경보 4건은 같은 방문인지 확인한 뒤 모두 해소됐다.

기존 간접 기록 14건의 시제 대조에서 현재형 감지는 R168의 2/6 → 3/6건, 오인은 0/8 → 0/8건이었다. 미래형은 감지 6/6·오인 0/8건이었다. 발신자와 수신자를 구분할 수 없는 앞 절은 추가 감지에서 제외했다. 새 제품 시험 17건은 수정 전 14/17 → 수정 후 17/17건이 통과했다. 별도 작성자의 자유 형식 92건과 현재형 18건에서는 R168과 비교해 등급 변화가 없었다.

## R176 · 상환금 수거 계획의 취소와 다른 방문의 취소 구분

기존 간접 보고 18건에 같은 계획이 취소됐다는 짧은 행정 메모를 쉼표 뒤에 붙이면 R174는 18건 모두 R18 위험 경보를 유지했다. 반대로 다른 발신자의 계획이 취소됐다고 적으면 18건 중 2건만 원래 경보를 유지했다. 수거를 제안한 주체와 보고 안의 방문을 먼저 연결하고, 같은 계획에 대해 확정된 마지막 상태를 적용했다. 한 절 안에서 방문이 여러 번 나와 대상이 불명확할 때는 새 취소 처리를 적용하지 않는다.

## R177 · 원래 번호로 통화한 가족의 답이 늦게 도착한 경우

부모님이 직접 원래 번호로 전화한 뒤 ‘안 보냈대요’를 고르면 기존 R5에 따라 해당 문자가 위험으로 올라간다. 확인 요청은 통상 5분 뒤에 만료되어도 원래 번호로 확인한 답을 받을 수 있다. 그러나 최초 분석 결과의 서명은 10분 뒤에 만료된다. R174에서는 요청과 검사 요약이 아직 남아 있어도 10분을 넘긴 답을 거절했다.

같은 보호 대상 계정이 보낸 사칭 확인 요청에서만, 원래 서명의 발급자 검증과 계정 대조를 거쳐 저장된 검사를 찾는다. 최초 서명의 해시·요청·검사가 일치하고 보관 기간 안이며 동의와 가족 연결이 유효한 경우, 그 검사 요약에 R5를 적용해 부모에게 결과를 다시 서명한다. 이 복구에서 새 기록이나 가족 알림을 만들지 않는다. 이미 다른 서명으로 바뀌어 원래 검사와 대조할 수 없는 경우에는 복구하지 않는다.

Chromium에서 실제 선택 화면과 판정 서비스를 연결하고 저장소 응답과 시계만 모의했다. 정상으로 연결된 요청에서 10분 직전, 정확히 10분, 11분이 지난 뒤 각각 ‘안 보냈대요’를 선택했다. 수정 전에는 첫 경우만 위험으로 표시됐고, 수정 후에는 세 경우 모두 같은 검사에 R5 위험이 표시됐다. 11분 뒤 ‘보냈대요’는 원래 주의, ‘통화가 안 돼요’는 확인 대기였다. 원래 검사 보관 기간 뒤의 복구는 거절됐다. 전후 12개 시나리오를 통과했다. 별도 로컬 API 시험으로 현재 동의, 대상 가족, 동시 재시도, 바뀐 검사에 대한 처리와 오판 신고에 전해지는 등급을 확인했다.

최종 로컬 시험은 코어 3,016개, 스킬 124개, 웹 193개, 평가 23개로 총 **3,356개**가 통과했다. 가족이 언제 답을 주었는지 기록되지 않은 평가 문자에 사용자의 답을 채워 넣지 않았다. 운영에서 이 수정으로 추가로 회복할 건수는 아직 측정할 수 없다.
